## 1. 电梯稿：30 秒介绍 FlowHub

> **30 秒版**：
> 「FlowHub 是一个企业级异步导出中心，解决的是『运营在页面点导出，50 万行数据当场查库生成 Excel』这条朴素路径在生产环境的所有死法：超时、OOM、重复提交、进度黑盒、服务重启任务卡死。它把导出从一个 HTTP 请求变成**有状态、可追踪、可恢复的异步任务**：创建时幂等裁决 + 同事务写 Outbox，RabbitMQ 可靠投递，消费者 CAS 抢占执行，Keyset 游标 + SXSSF 流式生成保证内存恒定，进度走 MySQL 事实源 + Redis 投影 + SSE 实时广播三层，文件原子发布后安全下载、过期自动清理。另有一套完全对称的 Excel 批量导入，额外解决了『300 行填错怎么办』——PARTIAL 部分成功 + 错误报告。」

面试官听到这段会自然产生追问点：**Outbox 是什么？CAS 怎么抢？内存怎么恒定？**——这正是我们想要的，每一个追问都通向一个你准备好的知识点。

一句话记忆锚点（画龙点睛用）：

> **「MySQL 是唯一事实源，Redis 只是投影，SSE 只是通知——每一层都允许失败，失败只降级、不污染事实。」**

## 2. STAR 条目：可以写进简历的 6 条

### ✍️ STAR 写法要领

简历里的 STAR 不是机械地「先背景再任务」，而是在两三句里自然融合四要素：

- **S+T 一带而过**：「在……场景下，为解决……问题」——凸显难度，不铺陈故事；
- **A 是核心**：方案动词用「设计/实现/落地」，多放技术术语（Outbox、CAS、Keyset、SSE）——每个术语都是给面试官的**追问钩子**，钩向你准备好的知识点；
- **R 用可复现的数字或结构性质收尾**：「内存占用与总行数无关」「实测 5 万行端到端 1.6MB」。

### 📌 数字口径（务必读）

FlowHub 是教学/演示项目，**所有写在简历里的数字必须能被你复现或指出来源**，否则面试一追问就露馅。本文条目使用的数字全部来自仓库真实配置与实测：

| 数字 | 来源 |
|---|---|
| 50 万行筛选导出上限 | 配置 `export.filter-max-rows` 默认值 |
| 内存恒定（窗口 100 行 + 每批 1000 行） | `ExcelExportWriter.ROW_WINDOW = 100`、`export.execution.batch-size` 默认 1000，**内存占用与总行数无关是结构性质** |
| 5 万行任务端到端通过、Excel 1.6MB | 真实联调记录（Playwright E2E 同链路） |
| `-Xmx512m` | 性能基线契约要求的受控 JVM 堆上限 |
| 重试上限 3 次、租约 5 分钟、文件保留 24h、SSE 心跳 15s、进度 RUNNING 封顶 99 | 代码常量与配置默认值 |

❌ 不要写「将成功率从 4% 提升到 100%」「内存峰值从 2.4GB 降至 320MB」这类**没有实测支撑的对比数字**——教学项目没有「投产前后的生产指标」，编造的基线是面试最容易翻车的地方。想要更漂亮的指标，用仓库的演示数据脚本（`seed-demo-data.sh` 可灌 100 万行）+ `-Xmx512m` 实际跑一轮，用复现的数字。

### 条目 1：异步化 + 事务性 Outbox 可靠投递

> **S+T**：运营侧高频导出（单次最高 50 万行）无法同步完成，且「任务创建成功但消息没发出去」会导致任务永远无人执行。
> **A**：我将导出重构为异步任务架构——创建接口做幂等裁决后，在同一数据库事务中写入 `export_jobs`(PENDING) 与 `outbox_events`；分发器定时扫描 Outbox 投递 RabbitMQ，仅收到 Publisher Confirm 且无退回才回填 `published_at`，失败/NACK/超时一律保留事件下轮补发，形成**至少一次投递**。
> **R**：消除了「业务落库」与「消息投递」之间的不一致窗口；实测 RabbitMQ 完全停机时创建接口照常 202 受理，Broker 恢复后自动补发消费，任务零丢失。

- 原型：`ExportJobService` + `OutboxDispatcher` + `RabbitConfig`（详见 [doc/03](03-导出任务创建与幂等.md)、[doc/04](04-可靠投递-Outbox与消费.md)）
- 可能的追问：「为什么不直接发 MQ？」→ 见 §4 Q1

### 条目 2：50 万行流式导出，内存恒定

> **S+T**：一次性加载全部命中数据生成 Excel，在数据量增长时必然 OOM，服务可用性被导出请求拖垮。
> **A**：我实现了「创建时定格 + 执行时流式」的读取管道：创建时单条 SQL 统计命中 COUNT 与范围内 MAX(id) 作为**高水位快照**；执行体按 `id > lastId AND id <= 高水位` 的 Keyset 游标每批 1000 行恒定成本推进，配合 POI SXSSF（滑动窗口 100 行，更早的行刷盘）流式写入，并对单元格文本做公式注入防护。
> **R**：内存占用与总行数无关；在 512MB 堆约束下实测 5 万行任务端到端生成 1.6MB Excel，配置上限 50 万行；高水位保证创建后新数据不混入本次导出（结果确定性）。

- 原型：`ExportOrderMapper.findBatch` + `ExcelExportWriter`（详见 [doc/05](05-导出执行与Excel生成.md)）
- 可能的追问：「为什么不用 OFFSET 分页？」→ 深分页 OFFSET 越翻越慢，Keyset 每批成本恒定；「为什么限定高水位？」→ 保证同一次请求的结果可复现

### 条目 3：多级幂等 + CAS 抢占，重复投递收敛为最多一次有效执行

> **S+T**：用户手抖重复点击、网络重试、MQ 重复投递、多实例并发消费，都会导致同一任务被执行多次。
> **A**：我设计了三层防护：① HTTP 层 `Idempotency-Key` + 规范化请求 SHA-256 指纹——同键同请求复用原任务、同键不同请求 409，并发同键由数据库唯一索引裁决；② 消费端手动 Ack，执行前以条件 UPDATE（`WHERE status='PENDING' AND attempt_count<3`）CAS 抢占，抢不到直接 Ack 放弃，同事务生成 Attempt 审计行（唯一索引防重复）；③ 所有状态迁移均为条件更新，配合租约心跳，服务重启时启动恢复将租约失效的 RUNNING 收敛为 FAILED，支持人工重试。
> **R**：重复投递、重复点击、并发消费被收敛为**最多一次有效执行**；每次执行留下不可覆盖的 Attempt 审计记录，失败可查「哪一次、为什么、跑了多久」。

- 原型：`ExportJobService.claimPendingJob` + `ExportJobAttemptMapper` + `ExportMaintenanceService`（详见 [doc/04](04-可靠投递-Outbox与消费.md)、[doc/08](08-恢复与清理.md)）
- 可能的追问：「幂等三态怎么裁决？」「为什么不自动重试？」→ 见 §4 Q2/Q6

### 条目 4：三层进度体系 + SSE 混合同步（前后端一条链）

> **S+T**：长任务执行期间用户零反馈，只能靠刷新和猜；而进度系统自身任何一层故障都不能污染任务事实。
> **A**：后端以 MySQL 条件 UPDATE 推进事实源（`processed_rows` 单调、终态单向、心跳续租，0 行更新立即 fail-fast），尽力写 Redis 进度投影（TTL 48h、失败仅记降级日志），事务**提交成功后**才经 SSE 广播（事件 id=`jobId:version`，RUNNING 进度封顶 99%）；前端 `useExportEvents` Hook 维护连接状态机，用 `job_version` 版本栅栏防御事件乱序，SSE 断线自动降级为按页面可见性区分频率的轮询，并以 HTTP 校准兜底。
> **R**：用户实时看到进度条；Redis 或 SSE 任一故障只影响「快」，不影响「对」——事实永远以 MySQL 为准；回滚的事务绝不广播假消息。

- 原型：`ExportProgressService` + `ExportSseService` + `useExportEvents`（详见 [doc/06](06-进度状态与SSE实时通知.md)、[doc/10](10-前端交互层.md)）
- 可再补的前端亮点：筛选**草稿与已提交严格分离**（表单输入不触发请求，点「查询」才提交并失效缓存）、**Blob 下载错误分流**（同一 URL 成功是文件流、失败是 JSON 错误包，统一解析转 `ApiError` 展示业务提示而非「下载失败」）、**翻页零位移**（`keepPreviousData` + 9 列固定宽度 + 滚动条占位）。
- 可能的追问：「Redis 挂了怎么办？」「为什么 AFTER_COMMIT 才广播？」→ 见 §4 Q3/Q5

### 条目 5：文件发布协议与路径安全

> **S+T**：用户可能下载到写了一半的 Excel；恶意构造的下载请求可能穿越目录读取任意文件；数据库登记失败会留下孤儿文件。
> **A**：我落地了发布协议：执行体先写 `.tmp` 临时文件，完成后同文件系统 `ATOMIC_MOVE` 原子改名发布，`markSucceeded` 事务登记成功才算存在，数据库提交失败则补偿删除未登记文件；文件全部落在受控 exportRoot 内，下载路径做**双层防腐**——文本层 normalize 拒绝 `..` 与根组件，物理层逐段符号链接检查 + `toRealPath` 验真；过期清理遵循「**删除成功才 EXPIRED**」，删除失败下轮再试，孤儿文件经「时间宽限 + 无活跃租约 + 无 DB 引用」三维对账后才删除。
> **R**：不存在「半个文件可下载」的状态；目录穿越与符号链接攻击被双层拦截；磁盘状态与数据库状态永远可对账。

- 原型：`ExportFileService` + `ExportMaintenanceService`（详见 [doc/07](07-文件安全与下载.md)、[doc/08](08-恢复与清理.md)）
- 可能的追问：「ATOMIC_MOVE 失败怎么办？」→ 不降级、直接走失败收敛，宁可任务失败不留半成品

### 条目 6：对称的 Excel 导入——三层校验 + PARTIAL 部分成功

> **S+T**：导入 10 万行 Excel 不能同步做完（对称于导出），且「一行填错全部回滚」是体验灾难；Excel 文件本身还是不可信输入。
> **A**：我将导入复刻为同构的异步任务管道（独立的 Outbox 拓扑与队列），上传受理做**三层校验**——文件级（后缀 + PK 魔数 + 10MB 上限）、结构级（Sheet 名/表头 9 列严格比对，同步 400 拒绝）、行级（格式/枚举/文件内查重/库内冲突预查，异步执行）；POI SAX 事件流边读边校验不全量加载；入库失败行不回滚有效行，终态收敛为 **PARTIAL 部分成功**并生成可下载的错误报告（行号与 Excel 对齐，`DuplicateKeyException` 逐行降级保证不产生重复订单）。
> **R**：单行错误不再导致全量失败，用户下载错误报告修正后重传即可；导入与导出表头格式互逆（列语义单一事实源），两端天然闭环。

- 原型：`ImportJobService` + `ExcelImportReader` + `ImportErrorReportWriter`（详见 [doc/09](09-订单Excel导入.md)）
- 可能的追问：「为什么 PARTIAL 不允许重试？」→ 见 §4 Q8

## 3. 渐进式叙事线：面试怎么讲故事

最有说服力的不是「我上来就设计了个完美系统」，而是**「朴素方案会在哪死 → 我怎么一步步补」**。FlowHub 的复盘文档天然就是这条叙事线，建议这样讲：

```
第 0 步（现状之死）：同步导出——50 万行当场查库生成 Excel
    → 超时 / OOM / 重复提交 / 进度黑盒 / 重启卡死（主文档 §1 的事故表）

第 1 步（异步化）：任务表 + 202 受理 + 后台执行
    → 新问题：任务写库成功、消息没发出去怎么办？→ 事务性 Outbox + Publisher Confirm

第 2 步（内存）：数据量上去就 OOM
    → 创建时定格高水位 + Keyset 游标批查 + SXSSF 滑动窗口

第 3 步（重复执行）：消息会重复投递、用户会重复点击
    → HTTP 幂等键 + request hash + CAS 条件抢占 + Attempt 审计

第 4 步（体验）：能导出了，但等 3 分钟像黑盒
    → MySQL 事实源 + Redis 投影 + AFTER_COMMIT SSE + 版本栅栏 + 轮询降级

第 5 步（异常收敛）：服务重启、文件半成品、磁盘泄漏
    → 租约 + 启动恢复 + ATOMIC_MOVE 原子发布 + 删除成功才 EXPIRED + 孤儿对账

第 6 步（对称问题）：导入是同样的异步问题 + 「部分失败怎么办」
    → 复刻同构管道 + 三层校验 + PARTIAL + 错误报告
```

**讲法技巧**：

- 每一步都用「但它带来了新问题」收尾，引出下一步——这证明你理解问题的**因果链**，而不是背方案清单；
- 面试官随时打断追问某一步，你就地展开该步的 STAR 条目（§2）与速查表（§5）；
- 主文档 §3 的时序图就是这条叙事的「白板版」，练习到能在 5 分钟内边画边讲。

## 4. 高频追问与参考回答

### Q1：「为什么不直接发 MQ，要绕一层 Outbox？」

直接发 MQ 的问题是「写库」和「发消息」不在同一个事务里：任务写入 MySQL 成功、发 MQ 时网络断了（或 MQ 挂了），任务就永远停在 PENDING。Outbox 的要点是把「要发消息」这件事本身**作为一行记录与业务同事务落库**，由独立分发器定时扫描投递、Confirm 后才打钩——MQ 挂了消息还在数据库里，恢复后自动补发。代价是消费端必须容忍重复投递（至少一次投递），这由 CAS 抢占收敛（Q2）。

### Q2：「怎么保证消息不重复消费 / 任务不被执行两次？」

三层：① **CAS 条件抢占**——`UPDATE ... SET status='RUNNING' WHERE status='PENDING' AND attempt_count<3`，affected rows = 1 才执行，= 0 说明别人抢了或已执行过，直接 Ack 当重复处理；② **Attempt 唯一索引** `uk_attempt_job_no` 从数据库层面防重复审计行；③ 创建侧幂等键唯一索引裁决并发重复创建（同键同 hash 复用、异 hash 409）。注意措辞：我们不承诺「恰好一次投递」（做不到），承诺的是「**重复投递收敛为最多一次有效执行**」——投递层至少一次 + 业务层幂等，这是业界标准组合。

### Q3：「Redis 挂了怎么办？」

Redis 在本项目里只是**可丢弃的加速投影**，不是事实源。进度事实在 MySQL 的 `processed_rows` 里有一份完整记录；Redis 写失败只记降级日志，应用照常运行；前端轮询接口读的本来就是 MySQL，SSE 广播走进程内连接表不经过 Redis。唯一损失是「读投影比读事实源快几毫秒」。这也回答了「为什么要用 Redis」——它只为高频读的活跃进度服务，且挂了不影响正确性，这是「缓存用在刀刃上」的示范。

### Q4：「这套方案支持多实例部署吗？」

如实回答：**当前是单机实现**（SSE 广播是进程内连接表、文件在本地盘），但架构已为多实例预留了最难的部分——CAS 条件抢占天然多实例安全（MySQL 行锁保证同一 job 只有一个实例抢到），Outbox 至少一次投递不依赖单机状态。要真正多实例还差三件事：SSE 跨实例 fanout（Redis Pub/Sub 或 MQ 广播）、共享文件存储（OSS/S3 + 预签名 URL）、维护任务的分布式锁或单实例选主。把「已知差距 + 演进路径」讲清楚，比假装支持更能体现工程判断。

### Q5：「为什么 SSE 事务提交后才广播？为什么不用 WebSocket？」

AFTER_COMMIT 才广播是因为：广播出去的消息必须**已经是事实**——如果事务回滚了而消息已发，前端就会展示一个从未发生的状态。实现上用 `@TransactionalEventListener(AFTER_COMMIT)` 且发送前重读 Job，保证事件内容与最终事实一致。选 SSE 而非 WebSocket 是因为场景是单向推送，SSE 走 HTTP 原生语义、断线重连简单、实现复杂度低一个量级；WebSocket 适合双向交互，这里用不上。

### Q6：「任务失败了为什么不自动重试？」

区分两类失败：**临时性失败**（如 Broker 抖动）由至少一次投递机制天然覆盖，消息还在队列里；**执行性失败**（数据问题、代码缺陷）自动重跑可能放大事故——比如数据本身有问题，重试三次只是烧三次资源。所以 `FAILED → PENDING` 只允许**人工重试**（条件重置 + 新 Outbox 事件，上限 3 次），失败 Attempt 历史完整保留，把「要不要再试」的决策留给人。这也是为什么 PARTIAL（部分成功）不允许重试：有效行已入库，重跑需要处理幂等语义，错误报告才是给用户的修复闭环。

### Q7：「怎么保证用户不会下载到半个文件？」

写盘与可见性分离：执行体全程只写 `.tmp` 临时文件，此时任务仍是 RUNNING、下载接口不会放行；写完才 `ATOMIC_MOVE` 原子改名为正式文件（同文件系统内改名是原子的），随后 `markSucceeded` 事务登记——登记成功之前文件对外不存在；登记失败则补偿删除文件。所以「可下载」这个状态的切换是原子的，不存在中间态。

### Q8：「导入为什么要有 PARTIAL 这种状态？」

批量导入的现实是「大概率有几行填错」。两种极端都不对：全部回滚（一行错全白填）和无脑全部入库（脏数据混进去）。PARTIAL 的语义是**部分成功**：有效行照常入库，错误行逐行记录原因生成错误报告，用户下载报告、在原 Excel 上修正、重新导入。配套的去重设计保证重传不产生重复订单：文件内查重 + 数据库 `order_no` 唯一约束兜底 + 冲突预查跳过已存在行 + `DuplicateKeyException` 逐行降级。这是一个「把错误还给用户、把一致性留给系统」的设计。

### Q9：「进度为什么 RUNNING 时封顶 99%？」

用户语义：**100% = 任务结束、文件可下载**。如果按行数比例算到 100% 但文件还没发布，用户点下载会失败——这是「进度条撒谎」。所以 RUNNING 阶段百分比封顶 99，只有 `markSucceeded` 落库后才真正置 100。小细节，但体现「进度是给用户的承诺，不是技术指标」。

## 6. 诚实边界：没做的部分怎么讲

面试官问「这项目有什么不足」时，**主动承认 + 给出演进路径**是加分项，支支吾吾才是减分项。FlowHub 的已知边界（主文档 §8）与讲法：

| 边界 | 讲法模板 |
|---|---|
| 🔐 无鉴权 | 「教学项目聚焦可靠性模式本身，鉴权是标准能力——接入 SSO、任务挂归属人、下载加归属校验即可，不影响核心架构」 |
| ☁️ 本地文件非对象存储 | 「文件协议已抽象为受控根目录 + 相对路径，换 OSS 只需替换文件服务实现 + 下载改预签名 URL」 |
| 🖥️ 单机部署 | 见 §4 Q4 的三步演进路径（fanout / 共享存储 / 选主） |
| 🧭 无前端路由 | 「本地状态切页是刻意简化，URL 同步属于常规工程补充」 |

一个万能句式：

> 「这些是**有意的取舍**——项目的价值密度在可靠性模式本身。每个边界我都清楚『要上生产需要补什么』，也都能说出具体方案。」

## 7. 延伸：这套模式还能讲成哪些业务故事

面试官常问「这个方案还能用在哪」——FlowHub 沉淀的模式是一套**通用异步任务骨架**，换业务皮就能讲成完全不同的项目。核心不变量始终是：**Outbox + CAS 抢占 + 幂等 + 流式处理 + 三层状态 + Attempt 审计**。

| 业务场景 | 换掉什么 | 重点复用的模式 |
|---|---|---|
| 报表生成（金融日报） | Excel 生成 → 跨库聚合计算 | 削峰（Consumer 并发控制）、Keyset 分批、Attempt 审计、SSE 进度 |
| 批量消息/邮件发送 | Excel 生成 → SMTP 调用 | Outbox 调度、限流 + 退避重试、Attempt 记录 SMTP 响应码 |
| 图片/视频转码 | Excel 生成 → FFmpeg/图像处理 | 异步解耦、并发控制、Checkpoint 恢复、原子发布 |
| AI 长任务 | Excel 生成 → LLM 调用 | 多阶段状态机、指数退避、Attempt 记录 token 归因、SSE 分页进度 |
| 跨系统数据同步 | 单次导出 → 增量同步 | Keyset 游标（`updated_at+id`）、断点恢复、对账审计 |
| 对账清算 | 导出 → 逐笔核对清算 | CAS 条件更新（幂等清算）、分批事务、Attempt 审计——**涉及资金时条件更新是底线** |

使用建议：简历上写 FlowHub 本身（真实可演示），面试口头交流时按对方公司业务**即兴换皮**——「我们这套模式如果放到你们的对账场景，会是……」，展示的是迁移能力而非背题。
